# API

Контракт между frontend и backend. Frontend вызывает эти маршруты через `frontend/api.js`. Backend реализован в `backend/`; FastAPI раздаёт интерфейс и API с одного origin. Проверки с тестовым генератором отделены от прогона настоящей Ollama.

## `GET /api/vehicles`

Модели и двигатели, по которым есть документы.

```json
{
  "vehicles": [
    {
      "model_code": "W213",
      "name": "E-класс",
      "body": "Седан",
      "years": "2016–2022",
      "engines": [
        { "code": "M264", "label": "M264 — бензин 2.0" },
        { "code": "OM654", "label": "OM654 — дизель 2.0" }
      ],
      "documents": 4
    }
  ]
}
```

`vehicles` может быть пустым: интерфейс сообщает, что доступных автомобилей пока нет. `model_code` уникален, `engines` — массив (допускается пустой), коды двигателей уникальны внутри модели. `body`, `name`, `years` — непустые строки. `documents` — необязательное целое число ≥ 0, не перечень названий. Без этого поля интерфейс не придумывает состав базы. Пользователь может не указывать двигатель; тогда поле `engine` отсутствует в запросе.

## `POST /api/ask`

**Запрос**

```json
{
  "question": "Что входит в сервис B?",
  "vehicle": { "model_code": "W213", "engine": "M264" }
}
```

| Поле | Тип | Обязательно | Описание |
| --- | --- | --- | --- |
| `question` | string | да | 1–500 символов |
| `vehicle.model_code` | string | да | `W205`, `W213` или `X253` |
| `vehicle.engine` | string | нет | Код двигателя; уточняет поиск, но не исключает общие фрагменты |

**Ответ 200** — одно из трёх состояний, поле `status`.

`answer` — ответ по найденным фрагментам:

```json
{
  "status": "answer",
  "intro": "Сервис B — расширенный объём работ по сравнению с сервисом A ...",
  "points": [
    { "text": "Замена моторного масла и фильтра ...", "citations": [1] }
  ],
  "warning": null,
  "sources": [
    {
      "n": 1,
      "chunk_id": "w213-manual-p412-c2",
      "doc_id": "w213-manual",
      "title": "Руководство по эксплуатации E-класса (W213)",
      "section": "Техническое обслуживание · ASSYST PLUS",
      "page": 412,
      "score": 8.41,
      "text": "Полный текст фрагмента ...",
      "matched_terms": ["сервис", "b"]
    }
  ]
}
```

`clarify` — запрос неоднозначен:

```json
{
  "status": "clarify",
  "message": "Какое масло вас интересует? Ответ зависит от узла автомобиля.",
  "options": [
    { "label": "Моторное масло", "question": "Какое моторное масло подходит для моего двигателя?" },
    { "label": "Масло в АКПП", "question": "Какое масло заливается в АКПП?" },
    { "label": "Тормозная жидкость", "question": "Какая тормозная жидкость нужна?" }
  ]
}
```

Нажатие на вариант отправляет его `question` как новый запрос.

`no_context` — в документах ответа нет:

```json
{
  "status": "no_context",
  "message": "В документах базы знаний нет ответа на этот вопрос.",
  "searched": [ { "doc_id": "w213-manual", "title": "Руководство по эксплуатации E-класса (W213)", "hits": 0 } ]
}
```

| Поле | Описание |
| --- | --- |
| `points[].citations` | Номера `n` из `sources`, на которые опирается пункт |
| `sources[].page` | Страница печатного руководства, а не номер страницы PDF-файла |
| `sources[].score` | Оценка BM25; показывается в панели фрагментов, но не как «процент уверенности» |
| `sources[].matched_terms` | Термы запроса после предобработки, найденные во фрагменте; frontend подсвечивает их |

`answer` содержит непустой `intro`, массив `points` и хотя бы один источник. У каждого пункта непустые `text` и `citations`; все сноски ссылаются на уникальные положительные целые `sources[].n`. У источника обязательны `chunk_id`, `doc_id`, `title`, `section`, `text` (непустые строки), `page` (положительное целое) и `score` (конечное число ≥ 0). `warning` допускает строку или `null`. Отсутствующий `matched_terms` трактуется как пустой массив; переданные элементы — непустые строки. Это визуальная подсветка, клиент не повторяет лемматизацию и поиск.

`searched[].hits` в КТ2 — число фрагментов документа в переданной top-k выдаче (для карточки 0 или 1), не число совпавших слов и не оценка BM25.

Для `clarify` нужны непустое сообщение и хотя бы один вариант с `label` и `question` (1–500 символов). Для `no_context` нужны сообщение и массив `searched` (может быть пустым); `hits` — целое число ≥ 0. Клиент не исправляет повреждённый ответ догадками.

**Ошибки**

| Код | Когда | Тело |
| --- | --- | --- |
| 400 | Пустой или слишком длинный вопрос | `{ "error": "question_invalid" }` |
| 404 | Неизвестная модель или недоступный код двигателя | `{ "error": "vehicle_unknown" }` |
| 503 | Недоступны LLM или индекс | `{ "error": "service_unavailable" }` |
| 500 | Внутренняя ошибка | `{ "error": "internal" }` |

При любой ошибке frontend показывает состояние «Ошибка» с кнопкой «Повторить».

Клиент различает HTTP-ошибку, отсутствие соединения, тайм-аут и неверный формат JSON/контракта. Текст технической ошибки сервера не выводится напрямую. Смена автомобиля отменяет запрос через `AbortController`; отмена не показывается как ошибка. Повтор загрузки моделей вызывает `GET /api/vehicles`, повтор вопроса — новый `POST /api/ask` с текущим автомобилем. Для отдельного frontend backend разрешает CORS с `http://localhost:8080` и `http://127.0.0.1:8080`; адреса должны совпадать с фактическим запуском frontend.

## `GET /api/health`

```json
{ "status": "ok", "index_loaded": true, "chunks": 1840, "llm": "available" }
```

В учебном корпусе КТ2 у всех моделей `engines: []`: карточки не содержат привязки к двигателю. Пример W213/M264 выше описывает формат будущего расширения, не фактический состав каталога. `GET /api/health` сообщает `status: "degraded"` при отсутствии индекса или выбранной модели Ollama; `llm: "available"` подтверждает наличие модели, но не гарантирует успешную генерацию.
