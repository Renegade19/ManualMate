# Способ проверки

## Контрольная точка 1

1. `python3 scripts/check_docs.py` — обязательные файлы, локальные ссылки, формат примера benchmark.
2. `node --check frontend/script.js` — синтаксис JavaScript (в GitHub Actions).
3. Открыть прототип по README и пройти сценарии S01–S05, S07–S09 из [scenarios.md](../product/scenarios.md).
4. Проверить ширину ноутбука (1440 px) и телефона (390 px).
5. Показать историю коммитов и Pull Request в GitHub.

Фактические результаты — [docs/verification.md](../../docs/verification.md).

| Индекс | `N`, `DF`, `avgdl`, `TF` совпадают с ручным расчётом на 3 документах из методички; `chunk_id` стабилен при повторной индексации | Backend |
| BM25 | Score совпадает с ручным расчётом по формуле; детерминированный порядок; пустой запрос и запрос без совпадений; фильтр по модели | Backend |
| API | Коды 200/400/404/503; три формы ответа; ссылки `[N]` указывают на существующие источники | Backend |
| LLM | Числа в ответе встречаются во фрагментах; при пустом контексте LLM не вызывается | LLM |
| Frontend | Все состояния отображаются; ошибка сервера не ломает интерфейс; ширина 390 px | Frontend |

Unit-тесты Python запускаются через `pytest` без GPU; LLM подменяется заглушкой.

## Benchmark

### Тестовый набор запросов

Около 60 запросов: **40 dev** (для настройки) и **20 holdout** (только для итоговой оценки). Из них около 10 — без ответа в корпусе и около 5 — неоднозначных (ожидается `clarify`).

**Равномерное покрытие корпуса.** Запросы распределяются по сетке «тема × модель»:

| Тема | W205 | W213 | X253 | Общие |
| --- | --- | --- | --- | --- |
| Сервис A и B, ASSYST PLUS | ✓ | ✓ | ✓ | ✓ |
| Моторное масло и допуски | ✓ | ✓ | ✓ | ✓ |
| Тормозная и охлаждающая жидкость | ✓ | ✓ | ✓ | ✓ |
| Фильтры, свечи, щётки | ✓ | ✓ | ✓ | |
| Шины и давление | ✓ | ✓ | ✓ | |
| Контрольные сообщения на панели | ✓ | ✓ | ✓ | |

**Как формулируем запросы** (не копированием фрагментов текста, как рекомендуют методические указания):

- от лица владельца и разговорной лексикой: «когда менять антифриз», «что за сервис B мне показывает машина»;
- перефразированием смысла раздела без его ключевых слов;
- вопросами-ситуациями: «загорелся гаечный ключ на панели, что делать».

**Релевантность.** Для каждого запроса размечается **не менее трёх** релевантных фрагментов (`relevant`). Разметку делает автор запроса, проверяет второй участник. Если в корпусе меньше трёх релевантных фрагментов, запрос переформулируется или заменяется.

Формат — [benchmark/README.md](../../benchmark/README.md).

### Метрики поиска

По методическим указаниям, `Q` — множество запросов, `R_q` — релевантные фрагменты запроса:

```text
Recall@k = 1/|Q| · Σ |R_q ∩ Top_k(q)| / |R_q|

MRR = 1/|Q| · Σ 1/rank_q,   rank_q — позиция первого релевантного фрагмента
```

Считаем Recall@3, Recall@5, Recall@10 и MRR (если релевантных нет в top-10, вклад запроса — 0). Для запросов без ответа — **точность отказа**: доля запросов, где система вернула `no_context`.

### Метрики ответа

Двое участников независимо оценивают ответы по шкале 0/1/2: правильность, опора на источник, полнота. Отдельно — доля ответов, где все числа есть во фрагментах.

### Эксперименты

| ID | Что сравниваем |
| --- | --- |
| E1 | Исходные слова против лемм (`pymorphy3`) |
| E2 | Без словаря синонимов против со словарём |
| E3 | Без фильтра по модели против с фильтром |
| E4 | Размер фрагмента: 400 / 800 / 1200 символов |
| E5 | Сетка `k1` ∈ {1.2, 1.5, 2.0} × `b` ∈ {0.5, 0.75, 1.0} на dev |
| E6 | Разные LLM при одинаковом поиске |

Предварительная цель: Recall@5 ≥ 0.7 и точность отказа ≥ 0.8 на holdout. Это ориентир, а не результат.

Каждый отчёт хранит commit, версию корпуса, параметры, модель LLM, результат по каждому запросу и время ответа. Holdout не используется для подбора параметров.
