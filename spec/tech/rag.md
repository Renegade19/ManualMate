# Спецификация RAG и BM25

## Корпус

**Документ** (по методическим указаниям) — отдельная индексируемая единица текста. У нас документ = **фрагмент** раздела руководства: страница или её часть, ограниченная заголовком раздела. Множество фрагментов — корпус.

Источники корпуса делятся на типы:

| `doc_type` | Что это | Модели |
| --- | --- | --- |
| `owner_manual` | Руководство по эксплуатации на русском | Отдельно W205, W213, X253 |
| `maintenance_booklet` | Сервисная книжка / буклет ТО: порядок сервисов, отметки | Все три |
| `service_scope` | Объём работ сервиса A и сервиса B, дополнительные работы | Все три |
| `fluids_spec` | Предписания по эксплуатационным материалам: масла (MB 229.5, 229.51, 229.52, 229.71), тормозная и охлаждающая жидкость | Все три, с привязкой к двигателям |

Перечень конкретных файлов и их статус проверки — [docs/sources.md](../../docs/sources.md). Формат хранения — [corpus/README.md](../../corpus/README.md).

Почему корпус удовлетворяет требованию «≥3 релевантных документа на запрос»: три модели делят двигатели и систему ASSYST PLUS, поэтому, например, вопрос о допуске масла для M264 находит фрагменты в руководстве W213, руководстве X253 и спецификации жидкостей.

## Извлечение текста

- PDF — постранично (`pypdf` или `pdfplumber`) с сохранением номера печатной страницы.
- Колонтитулы, номера страниц и оглавление удаляются.
- Таблицы регламента и спецификаций переводятся в строки вида «Позиция — значение — условие», каждая строка таблицы — отдельный фрагмент или часть фрагмента.
- Сканы без текстового слоя на первом этапе не включаются.

## Разбиение на фрагменты

- Граница — заголовок раздела; длинные разделы делятся по абзацам.
- Ориентир — 400–1200 символов, перекрытие одно предложение. Итог выбирается экспериментом E4.
- В начало фрагмента добавляется путь заголовков («Техническое обслуживание › ASSYST PLUS › Сервис B»): это помогает коротким запросам.
- Разделы, не относящиеся к обслуживанию (мультимедиа, навигация, ассистенты), помечаются `topic: other` и в индекс не попадают. Это сокращает шум.

Metadata фрагмента: `chunk_id`, `doc_id`, `doc_type`, `models` (список или `["*"]`), `engines`, `section`, `page`, `text`.

## Предобработка: токенизация и лемматизация

Одна функция `preprocess()` для корпуса и запроса (замечание 1.1 методических указаний).

1. **Защита обозначений** до разбиения: регулярные выражения находят и сохраняют целиком технические токены — вязкость (`5W-30`, `0W-20`), допуски (`MB 229.5` → `mb229.5`), коды двигателей и кузовов (`M264`, `OM654`, `W213`), классы жидкостей (`DOT 4+`), числа с единицами (`15 000 км` → `15000`, `км`).
2. **Нижний регистр** для остального текста. Аббревиатуры (`АКПП`, `ESP`, `ASSYST`) приводятся к нижнему регистру, но в лемматизатор не передаются.
3. **Токенизация** по словам: разделители — пробелы и пунктуация, кроме случаев из п. 1.
4. **Лемматизация** русских слов через `pymorphy3` («масла», «маслом» → «масло»; «замените» → «заменить»).
5. **Стоп-слова**: предлоги, союзы, частицы, местоимения. Отрицания («не», «нельзя») сохраняются — в регламенте они важны.
6. **Синонимы** (только для запроса): небольшой ручной словарь разговорных слов → термины руководства: «антифриз» → «охлаждающая жидкость», «тормозуха» → «тормозная жидкость», «коробка», «автомат» → «акпп», «ТО» → «сервис», «плановое обслуживание». Влияние проверяется экспериментом E2.

**Обоснование.** Без лемматизации запрос «когда менять масло» не совпадёт с «замена масла» и «масла» в документах — для русского языка это главная причина промахов BM25. Обычный лемматизатор разрушает технические обозначения («5W-30» → «5w», «30»), поэтому они защищаются до лемматизации. Синонимы нужны, потому что владельцы и руководство используют разную лексику, а запросы benchmark специально формулируются не копированием текста.

## Поиск BM25

Реализуется самостоятельно, готовые индексы не используются.

**Индекс** — инвертированный: `терм → список (chunk_id, TF)`. Дополнительно храним длину каждого фрагмента `|d|` в термах, `avgdl`, `N` и `DF(t)`.

**Оценка** по методическим указаниям:

```text
IDF(t) = ln(1 + (N − DF(t) + 0.5) / (DF(t) + 0.5))

BM25(q, d) = Σ_{t∈q} IDF(t) · TF(t,d)·(k1 + 1) / (TF(t,d) + k1·(1 − b + b·|d|/avgdl))
```

- Начальные параметры: `k1 = 1.5`, `b = 0.75`, `top_k = 5`. Подбираются на dev-запросах.
- **Фильтр по модели**: в ранжировании участвуют только фрагменты, у которых `models` содержит выбранную модель или `*`. `N`, `DF` и `avgdl` считаются по всему корпусу, чтобы IDF не зависел от выбора.
- Если выбран двигатель, фрагменты с другим явно указанным двигателем получают понижающий множитель (значение подбирается на dev), а не исключаются.
- **Порог отказа**: если score лучшего фрагмента ниже порога, подобранного на dev, ответ — `no_context`.

## Уточнение запроса

Запрос считается неоднозначным, если в нём есть терм из словаря неоднозначных («масло», «жидкость», «фильтр», «свеча») без уточняющего терма («моторный», «акпп», «тормозной», «салон», «воздушный» и т. п.). Тогда backend возвращает `clarify` с вариантами из словаря. Это правило проверяется отдельными запросами в benchmark.

## Генерация

Модель запускается локально через Ollama. Кандидаты — открытые instruct-модели 7–9B с хорошим русским языком; окончательный выбор делается по эксперименту E6 и записывается в [журнал решений](../decisions.md).

Prompt содержит:

- роль: помощник по обслуживанию Mercedes-Benz, отвечает только по приведённым фрагментам;
- автомобиль: модель и двигатель;
- фрагменты с номерами `[1]…[k]`, названием документа и страницей;
- вопрос;
- правила: каждое утверждение — со ссылкой `[N]`; числа (интервалы, объёмы, допуски) — только из фрагментов; если ответа во фрагментах нет — так и сказать; не давать советов по ремонту, которых нет в документах.

`sources` backend формирует из metadata фрагментов, а не из текста модели. Ссылки `[N]` на несуществующие фрагменты удаляются.
